# live-coding — плагін для live coding сесій з фронтендом

**Date:** 2026-08-27
**Status:** agreed
**Prototype:** —  (робота не має UI-поверхні; вивід — рядки в терміналі)

## 1. Проблема

Робота з фронтендом у Claude Code починається з одного й того самого ручного
ритуалу. Користувач щоразу просить підняти dev-інстанс, Claude щоразу заново
з'ясовує package manager і назву скрипта, запускає його, шукає порт у виводі.
У linked worktree до цього додається копіювання `.env*` і встановлення
залежностей — теж вручну і теж щоразу.

Далі йде другий розрив. Тип задач у такій сесії — короткі правки, які
користувач одразу бачить через hot-reload. Але наявні скіли налаштовані на
протилежне: `penny` будує викидний прототип у `docs/sdd/proto/`, замість того
щоб правити код, який уже відкритий у браузері; загальна поведінка тяжіє до
запуску тестів і перевірок у Playwright, яких у цьому режимі ніхто не просив.
Користувач витрачає повідомлення на те, щоб це вимкнути.

Третій розрив — на виході. Dev-сервер лишається жити після завершення сесії:
процеси накопичуються, порти лишаються зайнятими, наступний старт бере
випадковий порт.

## 2. Обмеження, що визначає рішення

**pasadena не редагується.** Плагін самодостатній: він не має права додати
жодного рядка в `penny/SKILL.md`, хоча саме поведінку `penny` він мусить
змінити. Це відкидає очевидний варіант — форк pasadena або гілку live-режиму
всередині її скілів.

Єдиний доступний важіль — контекст. Правила режиму мусять опинитися в контексті
моделі так, щоб пережити і `/clear`, і компакцію. Звідси конструкція з двох
джерел одного тексту: скіл `live` друкує правила при старті, а хук
`SessionStart` вкидає їх наново щоразу, коли контекст перезапускається при живій
сесії. Файл стану — те, що зв'язує ці два джерела: він і є визначенням
«live-сесія активна».

Друге обмеження — **worktree**. Користувач працює у linked worktree регулярно,
тому пам'ять плагіна розділяється надвоє: те, що стосується репозиторію
(обраний застосунок), має переживати створення нового worktree, а те, що
стосується запущеного процесу (pid, порт), — ні. Обидва місця мусять лежати
поза індексом git, не торкаючись `.gitignore` користувача.

## 3. Рішення

### 3.1 Склад плагіна

```
live-coding/
  .claude-plugin/plugin.json
  .claude-plugin/marketplace.json
  bin/live.sh
  commands/live.md
  commands/live-stop.md
  commands/do-it.md
  hooks/hooks.json
  skills/live/SKILL.md
  skills/do-it/SKILL.md
  README.md
```

Розподіл відповідальності: `bin/live.sh` володіє механікою (детект, bootstrap,
запуск, порт, зупинка) і не ухвалює рішень; скіли ухвалюють рішення і не
дублюють механіку.

`plugin.json`: `name: live-coding`, `hooks: ./hooks/hooks.json`, author
`dmytro-rudenko <ph.dmitry.rudenko@gmail.com>`, `license: MIT`, `version: 0.1.0`.
`marketplace.json` описує один плагін із `source: ./`.

Команди — тонкі обгортки: `commands/live.md` і `commands/do-it.md` викликають
однойменні скіли з `$ARGUMENTS`, `commands/live-stop.md` викликає
`bash "${CLAUDE_PLUGIN_ROOT}/bin/live.sh" stop` напряму, без скіла — там нема
чого вирішувати.

### 3.2 Стан

| Що | Шлях | Область дії |
|---|---|---|
| Конфіг | `$(git rev-parse --git-common-dir)/live/config.json` | спільний для всіх worktree репозиторію |
| Стан сесії | `$(git rev-parse --git-dir)/live/session.json` | окремий для кожного worktree |
| Лог dev-сервера | `$(git rev-parse --git-dir)/live/dev.log` | окремий для кожного worktree |

Поза git-репозиторієм обидва шляхи згортаються в `./.live/`.

`config.json`:

```json
{ "dir": "apps/web", "cmd": null }
```

`dir` — тека застосунку відносно кореня репозиторію. `cmd` заповнюється лише
тоді, коли dev-скрипт не вдалося визначити автоматично і користувач назвав
команду вручну; непорожній `cmd` має пріоритет над детектом.

`session.json`:

```json
{
  "pgid": 12345,
  "url": "http://localhost:5173",
  "port": 5173,
  "dir": "apps/web",
  "cmd": "pnpm run dev",
  "log": "/abs/path/.git/live/dev.log",
  "started": "2026-08-27T15:04:05Z"
}
```

Файл створюється лише після того, як URL реально знайдено. Сесія вважається
активною, коли файл існує **і** `kill -0 -- -<pgid>` успішний; інакше файл
вважається протухлим і видаляється.

### 3.3 `bin/live.sh`

Підкоманди, кожна друкує один рядок JSON:

**`detect`** — обходить репозиторій на глибину 3, ігноруючи `node_modules`,
`.git`, `dist`, `build`, і збирає кожен `package.json`, у якому є скрипт `dev`,
`start:dev` або `serve` (саме в цьому порядку пріоритету). Package manager
визначається по lock-файлу в корені репозиторію: `pnpm-lock.yaml` → `pnpm`,
`yarn.lock` → `yarn`, `bun.lock`/`bun.lockb` → `bun`, `package-lock.json` →
`npm`. За відсутності lock-файлу — поле `packageManager` з кореневого
`package.json`, за його відсутності — `npm`. Виводить масив кандидатів
(`{dir, script, pm}`) і поточний `config.json`.

**`start --dir <тека> [--cmd <команда>] [--open]`** — по черзі:

1. **Bootstrap, тільки в linked worktree.** Linked worktree визначається як
   `git rev-parse --git-dir` ≠ `git rev-parse --git-common-dir`. Шлях головного
   worktree — перший запис `git worktree list --porcelain`.
   1. Копіює з головного worktree кожен файл із маскою `.env*`, знайдений на
      глибину 3 повз `node_modules`, у відповідний відносний шлях. Наявний файл
      не перезаписується.
   2. Якщо `node_modules` у корені відсутній: коли lock-файли головного і
      поточного worktree байт-у-байт однакові (`cmp -s`), створює symlink на
      кореневий `node_modules` головного worktree і по одному symlink на кожен
      `<пакет>/node_modules`, який там існує. Інакше — `<pm> install`.
2. **Запуск.** `setsid nohup <команда> >dev.log 2>&1 &` із теки застосунку.
   `setsid` дає власну process-group; її pgid і зберігається. Команда — це
   `cmd` з конфігу, якщо він непорожній, інакше `<pm> run <script>`.
3. **Пошук URL.** Читає лог до 30 секунд, шукаючи
   `https?://(localhost|127\.0\.0\.1|\[::1\]):[0-9]+`. Перше влучання дає url і
   порт. Джерелом істини є саме лог, а не дефолтний порт фреймворку: коли
   дефолт зайнятий, vite та next мовчки беруть інший, і тільки лог про це знає.
   Якщо за 30 с URL не з'явився — фолбек `ss -ltnp` по pid'ах process-group.
4. **Страховка symlink'ів.** Якщо протягом того самого вікна очікування в лозі
   з'являється `Cannot find module`, `Cannot find package` або
   `command not found`, а `node_modules` є symlink'ом: symlink'и знімаються,
   виконується `<pm> install`, і робиться **рівно один** перезапуск. Другого
   разу немає — виводиться помилка зі шляхом до лога.
5. Записує `session.json`. За `--open` — `xdg-open <url>` (з фолбеком на `open`,
   потім `start`).

Повторний `start` при живій сесії нічого не запускає і повертає наявний стан.

**`stop`** — читає `session.json`, надсилає `kill -- -<pgid>` (TERM), чекає до
5 секунд, потім `kill -9 -- -<pgid>`. Group-kill обов'язковий: `pnpm run dev` —
це обгортка, і вбивство самого pnpm лишає vite живою сиротою на порту.
Видаляє `session.json`. Без файлу стану — тихий вихід із кодом 0.

**`status`** — стан сесії з перевіркою живості, або `{"active":false}`.

**`session-start`** — те, що викликає хук. При живій сесії друкує дайджест і
блок правил режиму (розділ 3.6). При неактивній — не друкує нічого.

### 3.4 Скіл `live` і команда `/live`

`/live` без активної сесії стартує її, з активною — друкує статус.

Старт: `detect`; один кандидат — стартує мовчки; кілька — одне питання через
`AskUserQuestion` зі списком тек, відповідь пишеться в `config.json`; жодного —
одне відкрите питання «якою командою підняти застосунок?», відповідь лягає в
`config.json` як `cmd`. Це і є підтримка не-Node стеків: `python manage.py
runserver`, `bin/rails s`, `make dev` працюють без жодного окремого коду.

Після старту скіл друкує URL, теку застосунку, шлях до лога і блок правил
режиму.

`bootstrap` виконується без підтвердження; це узгоджено окремо — тека worktree
без залежностей усе одно непрацездатна.

### 3.5 Скіл `do-it` і команда `/do-it`

Читає список пунктів, застосовує кожен, друкує один рядок на пункт. Не запускає
тести, не відкриває Playwright, не робить typecheck, не комітить. Результат
користувач бачить у браузері через hot-reload.

Дві причини не виконати пункт, і жодна з них не є «поміркувати ще»:

- **Пункт неоднозначний.** Скіл не вгадує. Він відкладає такий пункт, доробляє
  решту списку, і аж наприкінці ставить одне питання, що покриває всі відкладені
  пункти разом.
- **Пункт вимагає backend.** Рядок у `docs/live/deferred.md` і згадка у звіті.

Формат `docs/live/deferred.md` — плаский список, який дописується в кінець.
Файл створюється при першому записі:

```markdown
# Відкладено з live-сесій

## 2026-08-27 — фільтр за статусом у списку замовлень
**Потрібно:** `GET /api/orders` має приймати `?status=`.
**Чому не зараз:** live-сесія фронтендна, ендпоінт фільтра не має.
**Хто чекає:** `apps/web/src/pages/Orders.tsx` — селект уже є, фільтрує локально
завантажену сторінку замість усього набору.
```

Файл комітиться разом із кодом. Перетворення його на специфікацію — окрема
робота через `/bazinga`, і вона поза межами цього плагіна.

Скіл працює і поза live-сесією.

### 3.6 Правила live-режиму

Один і той самий текст друкує скіл `live` при старті і вкидає
`live.sh session-start` через хук. Дослівно:

> **LIVE CODING SESSION ACTIVE** — `<url>`, застосунок `<dir>`, лог `<log>`.
> Поки сесія активна:
> - **`penny` не будує прототип.** Ні теки `docs/sdd/proto/`, ні proto-сервера,
>   ні `decision.md`. Варіанти стають послідовними ітераціями по реальному коду:
>   внести зміну → сказати, куди дивитись → чекати вердикт користувача.
> - **Backend-розрив не реалізується.** Опис іде рядком у `docs/live/deferred.md`
>   (що потрібно, чому не зроблено зараз, який фронтенд на це чекає), робота
>   лишається фронтендною.
> - `sheldon`, `leonard`, `wolowitz`, `amy` працюють без змін. Явний запит на
>   повний SDD-цикл виконується як завжди.

### 3.7 Хуки

`hooks/hooks.json`:

| Подія | Матчер | Команда |
|---|---|---|
| `SessionStart` | `startup\|resume\|clear\|compact` | `bash "${CLAUDE_PLUGIN_ROOT}/bin/live.sh" session-start` |
| `SessionEnd` | `logout\|prompt_input_exit\|other` | `bash "${CLAUDE_PLUGIN_ROOT}/bin/live.sh" stop` |

`clear` свідомо відсутній у матчері `SessionEnd`: очищення контексту не є
завершенням роботи, вкладка в браузері лишається відкритою, а
`SessionStart` із тим самим `clear` одразу повертає правила режиму в контекст.

## 4. Поза межами

- Одночасний запуск кількох застосунків (фронтенд + бекенд парою). Одна
  live-сесія — один процес на worktree.
- Автоматичний перезапуск dev-сервера після падіння.
- Проксі, тунелі, HTTPS, кастомний host, окрім дефолтного біндингу самого
  фреймворку.
- Редагування будь-якого файлу плагіна pasadena.
- Керування браузером із боку Claude: `xdg-open` відкриває вкладку і на цьому
  участь плагіна в браузері закінчується.
- Читання console або network dev-сервера в межах live-режиму.

## 5. Прийняті компроміси

**Symlink на `node_modules` економить хвилини й іноді ламається.** Захист —
байт-у-байт порівняння lock-файлів перед symlink'ом і один автоматичний
відкат на повний install за сигнатурою помилки в лозі. Це покриває типовий
випадок розбіжності, але не покриває нативні модулі, зібрані під іншу гілку.

**Правила режиму живуть у контексті, а не у `penny/SKILL.md`.** Ціна прямо
випливає з вимоги не чіпати pasadena: розробник, який відкриє `penny/SKILL.md`,
не побачить там жодної згадки про live-режим. Компенсація — README плагіна
документує перевизначення явно.

**Порт береться з лога, тобто залежить від формату виводу фреймворку.** Регекс
покриває vite, next, nuxt, astro, remix і CRA. Екзотичний фреймворк, що не
друкує URL, лишиться без порту і піде у фолбек `ss -ltnp`, який залежить від
наявності `iproute2`.

**`do-it` не робить typecheck.** Свідомо: одна друкарська помилка може дати
білу сторінку, і користувач витратить хвилину на з'ясування. Взамін кожна
правка з'являється в браузері одразу, без паузи на перевірку.

**Стан у `.git/`.** Ніколи не комітиться і не потребує змін у `.gitignore`, але
менш помітний: користувач не знайде лог, не прочитавши вивід скіла.

## 6. Перевірка

1. **Детект.** У репозиторії з `pnpm-lock.yaml` і `apps/web/package.json` зі
   скриптом `dev`: `bash bin/live.sh detect` повертає список кандидатів
   рівно з одного запису — `{"dir":"apps/web","script":"dev","pm":"pnpm"}`.
2. **Старт і порт.** `/live` піднімає vite, друкує URL, вкладка відкривається.
   Порт у виводі збігається з тим, що слухає `ss -ltnp`. Повторний `/live`
   другого процесу не створює.
3. **Зайнятий порт.** Зайняти 5173 стороннім процесом, запустити `/live`:
   виведений URL містить порт, який vite обрав насправді, а не 5173.
4. **Worktree.** `git worktree add` без `.env` і без `node_modules`, потім
   `/live`: `.env` з'явився, `node_modules` — symlink, сервер піднявся.
5. **Відкат symlink'ів.** Той самий worktree з навмисно зміненим lock-файлом:
   symlink не створюється, йде повний install.
6. **Group-kill.** `/live-stop`, далі `pgrep -f vite` — порожньо, порт вільний.
7. **Переживання `/clear`.** При активній сесії `/clear`: dev-сервер живий,
   блок правил режиму знову в контексті.
8. **Автозупинка.** Вихід із Claude Code: `pgrep -f vite` порожньо,
   `session.json` видалено.
9. **`do-it`.** Список із трьох правок, одна з яких вимагає нового API-ендпоінта:
   дві правки застосовано, третя — рядком у `docs/live/deferred.md`, звіт із
   трьох рядків, жодного запуску тестів.
10. **`penny` в live-режимі.** Запит на порівняння варіантів UI: `docs/sdd/proto/`
    не створено, зміна внесена в реальний код.
